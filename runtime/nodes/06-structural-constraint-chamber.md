# 3. Runtime Prompt

# Reader-Facing Runtime Logic

The chamber opens with:

Where is the *system itself* slowing execution?

Not the people inside it.
The architecture they operate inside.

Where do:

* processes serialize what should run in parallel?
* decisions wait on the wrong person?
* tools fail to support the actual work?
* information arrives late, partial, or wrong?

The chamber narrows toward:

# the governing structural element.

Then:

* Is the strengthening: process redesign, tooling, information flow, decision architecture, or org boundary?
* What evidence supports this diagnosis? What contradicts it?

The chamber ends with:

# one structural intervention.

# 4. Internal Knowledge Base

## Rule 1 — Structures Are Slower Than They Look

Structural constraints often persist for years because nobody traces them to architecture. The runtime searches for old structure first.

## Rule 2 — Humans Mask Structural Failure

When a system requires heroic effort to function, the structure is weak, not the humans. Heroic effort = low-capacity architecture.

## Rule 3 — One Layer Governs

At any moment, one architectural layer is the dominant constraint. Process, decision, information, resource, or org design. Identify which.

## Rule 4 — Tooling Is Not Always The Answer

The chamber resists the SaaS reflex of solving structural problems with more tools. Often the structural change is *removing* a layer, not adding one.

## Rule 5 — Structure Reveals Itself Through Flow

Watch where work accumulates, where handoffs break, where decisions wait. Flow is the diagnostic.
